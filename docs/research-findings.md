## Predictive Serving Rooflines: An Analytical Model for LLM Inference Feasibility and ThroughputCapacity planning and latency forecasting for large language model (LLM) serving typically oscillate between two failure modes: static VRAM calculators that miscalculate dynamic runtime memory, and empirical probe runs that fail to generalize across heterogeneous compute tiers. Production inference splits into two distinct computational phases governed by fundamentally different physical bottlenecks. Single-stream autoregressive token generation is strictly bound by memory bus bandwidth, whereas prompt prefill and high-concurrency batched serving saturate the floating-point execution units of the processor.Evaluating whether a model will fit and estimating its generation speed across diverse architectures—from Apple Silicon unified memory to discrete GPUs and CPU-only hosts—can be resolved from hardware datasheets and Hugging Face config.json metadata alone without weight downloads or test executions. This is accomplished via a modular analytical model that separates hardware capability, structural parameter extraction, and engine-specific execution efficiency:$$\text{Fits} = \left( M_{\text{weights}} + M_{\text{kv\_cache}}(S_{\text{max}}, B) + M_{\text{activations}}(B) + M_{\text{safety}} \right) \le M_{\text{usable}}$$$$t_{\text{token}} = \max\left( \frac{B_{\text{read}}(c, B)}{\beta_{\text{sustained}}}, \frac{\text{FLOPs}(c, B)}{\pi_{\text{sustained}}} \right) + \tau_{\text{dispatch}} + \tau_{\text{interconnect}}$$Feasibility is resolved by testing required memory allocations against physical and operating-system-enforced memory ceilings. Per-token latency ($t_{\text{token}}$) and generation throughput ($T = B / t_{\text{token}}$) are evaluated across operational regimes by projecting memory and compute workloads onto an engine-corrected roofline model. By isolating active routing parameters, low-rank Key-Value latent geometries, recurrent state bounds, and fixed framework dispatch latencies, this modular framework eliminates the 2x to 4x forecasting errors typical of conventional estimators [cite: 8, context].Landscape Analysis and Public Calculator DeficienciesExisting capacity planning tools fall into four categories: academic roofline literature, hardware vendor profilers, engine scheduling heuristics, and web-based VRAM calculators. While each provides partial utility, all exhibit systematic deficiencies when evaluating non-datacenter or non-standard Transformer deployments.Academic roofline literature formalizes the relationship between arithmetic intensity and execution ceilings. However, published academic analyses treat the Transformer as an abstract, uniform stack of dense matrix multiplications. These models routinely omit architectural developments—such as Mixture-of-Experts (MoE) active routing, Multi-Head Latent Attention (MLA) compression, and State Space Model (SSM) recurrent buffers—while completely ignoring host runtime dispatch latencies.Hardware vendor tooling, such as NVIDIA GenAI-Perf and AMD ROCm profilers, captures kernel-level execution details with high precision. Nevertheless, these toolchains are coupled to proprietary software stacks (such as TensorRT-LLM) and enterprise hardware environments. They cannot evaluate cross-platform consumer deployments, such as Apple Silicon unified memory architectures or heterogeneous PCIe offloading. MLPerf Inference benchmarks provide robust empirical calibration data across standardized configurations (such as Llama-2-70B and Llama-3.1-405B under strict Time-to-First-Token [TTFT] and Time-per-Output-Token [TPOT] latency thresholds). However, MLPerf reports retrospective measurements on locked hardware configurations rather than an extrapolative predictive model.Public calculators (such as llm-vram-calculator, NyxKrage's calculator, and quantprobe) offer rapid estimations but introduce severe analytical errors:MoE Dimension Conflation: Multiple calculators extract the feed-forward layer size from intermediate*size rather than moe_intermediate_size. In models like DeepSeek-V2, where intermediate_size is 12,288 and moe_intermediate_size is 1,407, multiplying by total experts produces an overestimate exceeding 300 billion parameters [cite: 39, context].Active versus Resident Weight Confusion: Standard tools evaluate memory bandwidth demand during decode by dividing total model weight bytes by bus bandwidth, ignoring that MoE architectures read only active expert weights per token.Apple Silicon Memory Architecture Blindness: Calculators routinely omit Apple Silicon "Pro" tier chips (such as the M2 Pro, M3 Pro, and M4 Pro) and mishandle unified memory. macOS clamps single-process GPU allocations via the kernel setting sysctl iogpu.wired_mem_limit, which defaults to roughly 75% of physical RAM unless explicitly tuned by the operator.KV-Cache Naivety: KV cache is routinely treated as a static buffer or sized assuming standard Multi-Head Attention (MHA), ignoring Grouped-Query Attention (GQA), sliding-window limits, and MLA low-rank projections.Fixed Dispatch Erasure: Elementary tools assume execution latency scales toward zero as model size decreases. The operational boundary between these regimes is governed by arithmetic intensity relative to the hardware's machine balance.Arithmetic intensity ($I$) is defined as the ratio of floating-point operations executed to memory bytes moved across the hardware bus:$$I = \frac{\text{FLOPs}}{\text{Bytes Transferred}} \quad \left[\frac{\text{FLOP}}{\text{Byte}}\right]$$Hardware accelerators exhibit a machine balance ridge point ($I_{\text{ridge}}$) defined by peak sustained compute ($\pi$, in FLOP/s) divided by sustained memory bandwidth ($\beta$, in Bytes/s) at the target numerical precision:$$I_{\text{ridge}} = \frac{\pi}{\beta}$$If $I < I_{\text{ridge}}$, execution is memory-bandwidth-bound: the execution pipelines stall while waiting for data from DRAM. If $I > I_{\text{ridge}}$, execution is compute-bound: memory transfers are hidden behind arithmetic execution.Single-Stream Autoregressive DecodeDuring single-stream token generation ($B = 1$), a single token vector of dimension $1 \times d_{\text{in}}$ multiplies weight matrices $W \in \mathbb{R}^{d_{\text{in}} \times d_{\text{out}}}$. Generating each token requires fetching the model weights from DRAM into registers to perform a matrix-vector product:$$\text{FLOPs} = 2 \cdot d_{\text{in}} \cdot d_{\text{out}}$$$$\text{Weight Bytes Read} = d_{\text{in}} \cdot d_{\text{out}} \cdot b_{\text{weight}}$$Here, $b_{\text{weight}}$ denotes the storage bytes per parameter (such as $2.0$ for FP16, $1.0$ for FP8, and $0.5$ for INT4). Neglecting cache reuse, the arithmetic intensity of this decode step is:$$I_{\text{decode, weights}} = \frac{2 \cdot d_{\text{in}} \cdot d_{\text{out}}}{d_{\text{in}} \cdot d_{\text{out}} \cdot b_{\text{weight}}} = \frac{2}{b_{\text{weight}}}$$For 16-bit weights, $I = 1.0\text{ FLOP/byte}$; for 4-bit weights, $I = 4.0\text{ FLOP/byte}$. Modern computing hardware exhibits machine balance points between $100$ and $350\text{ FLOP/byte}$ (for instance, an NVIDIA H100 SXM features $989.5\text{ TFLOP/s}$ BF16 dense compute and $3,350\text{ GB/s}$ HBM3 bandwidth, giving $I_{\text{ridge}} \approx 295\text{ FLOP/byte}$; an RTX 4090 features $165\text{ TFLOP/s}$ dense FP16 compute and $1,008\text{ GB/s}$ GDDR6X bandwidth, giving $I_{\text{ridge}} \approx 164\text{ FLOP/byte}$). Because $I_{\text{decode}} \ll I_{\text{ridge}}$, single-stream decode operates deep within the memory-bandwidth-bound regime.Prompt PrefillDuring prompt prefill, the engine processes an input sequence of length $S_{\text{prompt}}$ in parallel. The operation becomes a matrix-matrix multiplication (GEMM) where an input activation matrix $X \in \mathbb{R}^{S_{\text{prompt}} \times d_{\text{in}}}$ multiplies weight matrix $W \in \mathbb{R}^{d_{\text{in}} \times d_{\text{out}}}$:$$\text{FLOPs} = 2 \cdot S_{\text{prompt}} \cdot d_{\text{in}} \cdot d_{\text{out}}$$$$\text{Bytes Read} = (d_{\text{in}} \cdot d_{\text{out}} \cdot b_{\text{weight}}) + (S_{\text{prompt}} \cdot d_{\text{in}} \cdot b_{\text{act}})$$As $S_{\text{prompt}}$ scales into thousands of tokens, weight transfers are amortized across all tokens in the sequence, driving arithmetic intensity upward:$$I_{\text{prefill}} \approx \frac{2 \cdot S_{\text{prompt}} \cdot d_{\text{in}} \cdot d_{\text{out}}}{d_{\text{in}} \cdot d_{\text{out}} \cdot b_{\text{weight}}} = \frac{2 \cdot S_{\text{prompt}}}{b_{\text{weight}}}$$For $S_{\text{prompt}} = 1,024$ at 16-bit precision, $I_{\text{prefill}} \approx 1,024\text{ FLOP/byte}$. Because $I_{\text{prefill}} > I_{\text{ridge}}$, the prefill phase saturates the accelerator's matrix arithmetic pipelines and is strictly compute-bound.Derivation of the Crossover Batch SizeIn multi-user serving, incoming decode streams are batched together. Concatenating $B$ independent decode requests forms an input matrix of shape $B \times d_{\text{in}}$, executing a batched GEMM against the model weights. The weight tensors are read once from DRAM and reused across all $B$ requests.The arithmetic intensity of the batched weight computation scales linearly with batch size:$$I_{\text{batched}}(B) \approx \frac{2 \cdot B}{b_{\text{weight}}}$$The crossover batch size ($B^*$) at which a workload shifts from memory-bandwidth-bound to compute-bound occurs where the workload's arithmetic intensity matches the hardware ridge point:$$\frac{2 \cdot B^*}{b_{\text{weight}}} = I_{\text{ridge}} = \frac{\pi}{\beta} \implies B^* = \frac{\pi \cdot b_{\text{weight}}}{2 \cdot \beta}$$Hardware PlatformPeak Compute π (FP16/BF16)Sustained Memory Bandwidth βMachine Balance Iridge​Crossover Batch B∗ (FP16, 16-bit)Crossover Batch B∗ (INT4, 4-bit)NVIDIA H100 SXM5989.5 TFLOP/s (Dense)3,350 GB/s295.4 FLOP/B29674NVIDIA RTX 4090165.0 TFLOP/s (Dense)1,008 GB/s163.7 FLOP/B16441Apple M4 Pro (20-core GPU)27.3 TFLOP/s273 GB/s100.0 FLOP/B10025Apple M4 Max (40-core GPU)54.6 TFLOP/s546 GB/s100.0 FLOP/B10025Dual-Channel DDR5-5600 (CPU)2.5 TFLOP/s (AVX-512)65 GB/s (Sustained)38.5 FLOP/B3910At batch sizes $B < B^*$, throughput scales near-linearly with batch size because weight reads remain constant while useful compute increases. Beyond $B^*$, the hardware saturates its compute pipelines; per-token latency increases linearly with batch size, and aggregate token throughput plateaus at the hardware compute roof.Dynamic KV-Cache Bandwidth Scaling During DecodeElementary roofline formulations treat decode memory traffic as a static weight fetch. At step $c$ of sequence generation, the attention mechanism must read the accumulated Key and Value states of all preceding tokens to compute attention distributions.For a model with $L$ layers, $n_{\text{kv}}$ key-value heads, head dimension $d_{\text{head}}$, and KV cache precision $b_{\text{kv}}$ bytes per element, the bytes transferred across the memory bus to read the KV cache for a single decode step at context position $c$ are:$$B_{\text{kv\_read}}(c) = 2 \cdot L \cdot n_{\text{kv}} \cdot d_{\text{head}} \cdot b_{\text{kv}} \cdot c$$Total data transferred per decode step is the sum of active model weights and the context-dependent KV cache:$$B_{\text{read}}(c) = W_{\text{active}} + B_{\text{kv\_read}}(c)$$For an 8-billion parameter model in 4-bit precision (such as Llama-3-8B, where $W_{\text{active}} \approx 4.5\text{ GB}$), generating at context length $c = 1,024$ requires reading $134.2\text{ MB}$ of KV cache per token—representing under $3\%$ of total memory traffic. However, at $c = 32,768$, the KV cache read expands to $4.29\text{ GB}$ per step, matching the data volume of the weights themselves. At $c = 128,000$, the KV cache read reaches $16.78\text{ GB}$ per token, accounting for $79\%$ of all memory traffic. Single-stream decode speed degrades significantly as context length increases:$$t_{\text{decode}}(c) = \frac{W_{\text{active}} + (2 \cdot L \cdot n_{\text{kv}} \cdot d_{\text{head}} \cdot Instead of saving full key-value head tensors to DRAM, MLA projects keys and values into a single low-rank latent vector $\mathbf{c}_t^{\text{KV}}$ of dimension $d_c$, paired with a decoupled rotary vector $\mathbf{k}_t^{\text{R}}$ of dimension $d_{\text{head}}^{\text{R}}$.The architectural dimensions are extracted from config.json:KV compression latent rank: $d_c = \text{config.json}[\texttt{"kv\_lora\_rank"}]$ (e.g., $512$)Query compression latent rank: $d_c' = \text{config.json}[\texttt{"q\_lora\_rank"}]$ (e.g., $1,536$)Decoupled key/query RoPE dimension: $d_{\text{head}}^{\text{R}} = \text{config.json}[\texttt{"qk\_rope\_head\_dim"}]$ (e.g., $64$)Decoupled non-RoPE dimension: $d_{\text{head}}^{\text{NOPE}} = \text{config.json}[\texttt{"qk\_nope\_head\_dim"}]$ (e.g., $128$)Value head dimension: $d_{\text{head}}^{\text{V}} = \text{config.json}[\texttt{"v\_head\_dim"}]$ (e.g., $128$)At inference time, runtimes execute weight absorption: the upward projection matrices for keys and values ($W^{\text{UK}}$ and $W^{\text{UV}}$) are folded into the query projection and output projection matrices during decode. The engine caches only the latent vector and the decoupled positional key per token:$$\text{Elements Cached per Token per Layer} = d_c + d_{\text{head}}^{\text{R}}$$For standard GQA or MHA, the cached elements per token per layer are $2 \cdot n_{\text{kv}} \cdot d_{\text{head}}$. For DeepSeek-V3, standard MHA with $n_{\text{q}} = 128$ and $d_{\text{head}} = 128$ would require caching $2 \cdot 128 \cdot 128 = 32,768$ elements per token per layer. MLA caches $512 + 64 = 576$ elements per token per layer—an exact $56.9\times$ reduction in KV cache memory footprint and memory-bus read traffic.Sliding-Window and Local Attention BoundsWhen a model configuration specifies a sliding-window constraint (such as $\texttt{"sliding\_window"}: 4096$ in Mistral models), the attention mechanism restricts KV-cache access to the most recent $W_{\text{window}}$ tokens:$$c_{\text{eff}}(c) = \begin{cases} c & \text{if } c \le W_{\text{window}} \\ W_{\text{window}} & \text{if } c > W_{\text{window}} \end{cases}$$In architectures employing alternating sliding-window and global attention layers (such as Gemma-2), layers must be evaluated as an indexed set $\mathcal{L}$. For layer $l \in \{1, \dots, L\}$, the active context $c_{\text{eff}}(l, c)$ is clamped based on layer type:$$B_{\text{kv\_read}}(c) = \sum_{l=1}^L 2 \cdot n_{\text{kv}}^{(l)} \cdot d_{\text{head}}^{(l)} \cdot b_{\text{kv}} \cdot c_{\text{eff}}(l, c)$$This transformation caps KV-cache memory consumption and prevents per-token memory read traffic from scaling unboundedly at long contexts.Hybrid Transformer and State-Space Model LayersHybrid architectures (such as Jamba) interleave standard Transformer attention layers with recurrent State Space Model (SSM) blocks (Mamba). The layer composition is extracted from structural metadata:Transformer layer set: $\mathcal{L}_{\text{attn}}$Mamba SSM layer set: $\mathcal{L}_{\text{ssm}}$SSM state dimension: $d_{\text{state}} = \text{config.json}[\texttt{"mamba\_d\_state"}]$ or $\texttt{"d\_state"}$ (e.g., $16$)SSM convolution width: $d_{\text{conv}} = \text{config.json}[\texttt{"mamba\_d\_conv"}]$ or $\texttt{"d\_conv"}$ (e.g., $4$)SSM inner expansion: $d_{\text{inner}} = \text{config.json}[\texttt{"mamba\_expand"}] \cdot d$ (typically $2 \cdot d$)Mamba layers do not accumulate an expanding KV cache across sequence generation. Instead, they maintain a fixed-size recurrent state representation per sequence:$$M_{\text{state\_single}} = B \cdot d_{\text{inner}} \cdot (d_{\text{state}} + d_{\text{conv}} - 1) \cdot b_{\text{state}}$$During decode, memory read traffic for an SSM layer is constant with respect to context length $c$:$$B_{\text{read, ssm}} = W_{\text{ssm}} + M_{\text{state\_single}}$$The dynamic KV read traffic for the entire hybrid model across context length $c$ is restricted strictly to the attention layers:$$B_{\text{kv\_read, hybrid}}(c) = \sum_{l \in \mathcal{L}_{\text{attn}}} 2 \cdot n_{\text{kv}} \cdot d_{\text{head}} \cdot b_{\text{kv}} \cdot c$$In a 3:1 Mamba-to-Attention architecture (such as Jamba), KV memory traffic accumulates at only $25\%$ of the rate observed in standard Transformer configurations.Mixed and Per-Layer Quantization OverridesDeployment formats (particularly GGUF executed via llama.cpp) employ non-uniform quantization bit-widths across tensor hierarchies. A global bits-per-weight assumption underestimates memory footprints. The parameter-to-bit mapping must be calculated across tensor classes:$$M_{\text{weights}} = \sum_{t \in \mathcal{T}} P_t \cdot b_t + M_{\text{quant\_metadata}}$$In standard GGUF Q4*K_M configurations:Attention and MLP down-projection weights use 4.5 bits per weight (Q4_K superblocks: 256 elements grouped with 16-bit block scales).Feed-forward gate and up-projections use Q4_K or Q5_K (5.5 bits per weight).Input embeddings (embed_tokens) and output heads (lm_head) frequently remain quantized at higher precisions, such as Q6_K (6.56 bits) or unquantized 16-bit FP16/BF16 (16.0 bits), to preserve vocabulary-level cross-entropy performance.Metadata scales and quantization offsets ($M*{\text{quant_metadata}}$) introduce an overhead of $0.05$ to $0.25$ bits per weight that must be incorporated into total weight volume calculations.Multi-Token Prediction HeadsModern architectures (such as DeepSeek-V3) train secondary multi-token prediction (MTP) modules to predict multiple future tokens simultaneously. This metadata is specified via:$$N_{\text{mtp}} = \text{config.json}[\texttt{"num\_nextn\_predict\_layers"}]$$Each MTP module consists of an independent RMSNorm, a projection layer ($eh\_proj \in \mathbb{R}^{2d \times d}$), and a full Transformer layer.Standard Autoregressive Decode: If the serving engine does not explicitly activate MTP speculative verification, these layers are excluded from the execution graph. They reside in DRAM ($M_{\text{weights}}$ must account for their parameter footprint, adding roughly $11.5\text{ billion}$ parameters in DeepSeek-V3), but they are not fetched across the memory bus during generation steps, contributing zero bytes to $W_{\text{active}}$.MTP Speculative Decoding: If the engine executes MTP-driven speculative decoding, the MTP heads enter the execution path to verify $K$ speculative tokens in parallel, amortizing weight fetch costs.Speculative Decoding DynamicsSpeculative decoding employs a smaller draft model or internal prediction heads to propose $\gamma$ candidate tokens, followed by a parallel verification pass on the target model. This serving configuration alters effective tokens generated per second without altering the base execution speed of the target model.Given an empirical draft acceptance rate $\alpha \in [0, 1]$, the expected number of accepted tokens per verification cycle is:$$\mathbb{E}[\text{tokens per step}] = \frac{1 - \alpha^{\gamma + 1}}{1 - \alpha}$$The latency incurred per verification cycle comprises $\gamma$ serial steps of the draft engine plus a single batched verification pass of size $\gamma + 1$ on the target model:$$t_{\text{cycle}} = \gamma \cdot t_{\text{draft}} + t_{\text{target\_prefill}}(\gamma + 1)$$$$\text{Effective Speed} = \frac{\mathbb{E}[\text{tokens per step}]}{t_{\text{cycle}}} \quad \left[\frac{\text{tok}}{\text{s}}\right]$$Multimodal Vision-Language TowersIn multimodal architectures (such as Qwen2-VL), vision parameters are isolated under a sub-configuration dictionary:$$\text{Vision Config} = \text{config.json}[\texttt{"vision\_config"}]$$The visual encoder is parameterized by patch dimensions (patch*size, spatial_merge_size), hidden channel depth (embed_dim), and transformer layer counts (depth).Prefill Impact: Input images are tokenized into visual token grids:$$N*{\text{visual_tokens}} = \left( \frac{H}{\text{patch_size} \cdot \text{spatial_merge_size}} \right) \cdot \left( \frac{W}{\text{patch_size} \cdot \text{spatial_merge_size}} \right)$$These visual tokens are prepended to the text prompt sequence, increasing the effective prefill context length to $S_{\text{prompt}}' = S_{\text{text}} + N_{\text{visual\_tokens}}$, scaling prefill compute and initial KV-cache allocation.Decode Impact: During autoregressive text generation, the vision encoder is inactive. On Metal and CUDA backends, vectorized dot-product intrinsics (DP4A, MMA) achieve $\eta_{\text{bw}} \approx 0.80\text{--}0.85$.MLX Affine Quantization: Apple Silicon MLX employs 4-bit affine quantization, packing two weights per byte with associated floating-point scale and bias terms. Because Apple Silicon Unified Memory uses a unified LPDDR physical bus, memory accesses are subject to stride alignment constraints in the Metal shader compiler, achieving $\eta_{\text{bw}} \approx 0.82\text{--}0.86$.Fixed Framework Dispatch OverheadElementary roofline models assume kernel execution time approaches zero as parameter size decreases. However, every decode step incurs host-to-device launch latencies, framework synchronization costs, and driver command-buffer submission overheads [cite: context]:$$t_{\text{step}} = t_{\text{hardware}} + \tau_{\text{dispatch}} = \frac{B_{\text{read}}}{\eta_{\text{bw}} \cdot \beta_{\text{sustained}}} + \tau_{\text{dispatch}}$$On Apple Silicon running MLX, host Python framework overhead combined with Metal command-buffer encoding and thread synchronization imposes an additive latency floor:$$\tau_{\text{dispatch, MLX}} \approx 6.7\text{--}9.6\text{ ms} \quad (\text{Mean } \tau \approx 7.8\text{ ms}) \text{ [cite: context]}$$On an Apple M4 Pro system ($273\text{ GB/s}$ bandwidth), generating tokens for a 1-billion parameter 4-bit model ($W \approx 0.6\text{ GB}$) requires an ideal memory read time of $0.6 / 232 \approx 2.58\text{ ms}$. Without modeling dispatch overhead, the roofline predicts $387\text{ tokens/s}$. Adding the fixed dispatch overhead ($\tau_{\text{dispatch}} = 7.8\text{ ms}$) yields a step time of $2.58 + 7.8 = 10.38\text{ ms}$, or $96.3\text{ tokens/s}$—accurately capturing why small models hit an early latency ceiling [cite: context].In enterprise runtimes such as vLLM and TensorRT-LLM, static CUDA graph execution captures the entire layer execution graph during warmup. The host processor issues a single graph launch IOCTL per forward pass, reducing dispatch overhead to $\tau_{\text{dispatch}} \approx 0.1\text{--}0.3\text{ ms}$.Hybrid Interconnect Layer OffloadingWhen model size exceeds GPU memory capacity, llama.cpp supports partitioning transformer layers across system RAM and discrete GPU VRAM via the --n-gpu-layers ($N_{\text{gpu}}$) flag:GPU-resident layers: $l \in [1, N_{\text{gpu}}]$ executed on GPUCPU-resident layers: $l \in [N_{\text{gpu}} + 1, L]$ executed on CPUAutoregressive token generation is strictly sequential: layer $l+1$ cannot execute until layer $l$ finishes emitting its activation tensor. Layer offloading operates as a pipelined execution path where hardware execution units run in sequence rather than in parallel:$$t_{\text{step}} = t_{\text{gpu\_layers}} + t_{\text{cpu\_layers}} + t_{\text{pcie\_transfer}}$$The intermediate hidden state tensor ($X \in \mathbb{R}^{B \times d_{\text{model}}}$) must be transferred across the PCIe bus twice per decode step: once from GPU to CPU at the layer split boundary, and once from CPU to GPU to complete the final layer normalization and vocabulary projection (if lm*head is mapped to the GPU):$$t*{\text{pcie_transfer}} = \frac{2 \cdot B \cdot d*{\text{model}} \cdot b*{\text{act}}}{\beta*{\text{pcie}}}$$The component execution times are defined by their respective memory buses:$$t*{\text{gpu_layers}} = \frac{(N*{\text{gpu}} / L) \cdot W*{\text{active}} + B*{\text{kv_gpu}}(c)}{\beta*{\text{vram}}}$$$$t*{\text{cpu_layers}} = \frac{((L - N*{\text{gpu}}) / L) \cdot W*{\text{active}} + B*{\text{kv_cpu}}(c)}{\beta*{\text{system_ram}}}$$Because system DDR RAM bandwidth ($\beta*{\text{system_ram}} \approx 40\text{--}80\text{ GB/s}$) is an order of magnitude slower than discrete VRAM ($\beta*{\text{vram}} \approx 500\text{--}1,000\text{ GB/s}$), the CPU-resident layers dominate the execution budget. The model assumes uniform expert distribution across concurrent batches.CPU Cache Hierarchy Interactions: On CPU-bound architectures, memory access patterns interact complexly with multi-level on-chip caches (L1, L2, and shared L3/3D V-Cache). For small models whose active weights fit within L3 cache ($>96\text{ MB}$), generation speed transitions from DRAM-bandwidth-bound to L3-cache-bandwidth-bound ($>1\text{ TB/s}$), producing speeds significantly higher than predicted by DDR bus formulas.Operating System Swapping Collapse: When memory requirements exceed physical RAM, operating system virtual memory managers page memory blocks to NVMe storage. Because NVMe read bandwidth ($3\text{--}7\text{ GB/s}$) is an order of magnitude slower than system DRAM, entering swap causes generation speeds to collapse by $95\text{--}99\%$. The model treats the physical memory boundary as a hard feasibility failure.Prefix Caching Hit Rates: Production serving engines implement automatic prefix caching (RadixAttention), reusing pre-computed KV blocks for common system prompts. Because prefix hit rates depend on dynamic user traffic distributions, the model calculates prefill latency assuming cold-cache invocations.Relying on empirical probe scripts or uncalibrated heuristic calculators introduces severe risks of infrastructure over-provisioning and out-of-memory crashes. By grounding feasibility and latency forecasting in a modular framework—anchored by the physical memory bandwidth roofline, parameterized by explicit configuration metadata, and adjusted for engine dispatch overheads—systems engineers can accurately predict operational performance across heterogeneous hardware architectures before allocating capital or deploying workloads.
